# Plugin 2.0.0 decisions (2026-10-10)

Taken by Claude under the owner's delegation (monorepo decision log row 57: "everything else you can build without asking, taking decisions (while documenting them)"). The owner can override any of them; each says what changes then. Plan: monorepo `docs/plans/32-track-c-surfaces.md`, item C.2.

1. **2.x server only, no score fallback.** The skill needs `estimate_run`, `start_run`, `get_run`, `get_ladder`, `list_issues`; without them it tells the user this version needs the 2.x server and stops. It does not use the one-release wrappers `analyze_repo`, `get_report`, `get_findings` (`analyze_repo` can start a paid check in one call, before the user has seen the price). Reason: one ladder on every surface, no score anywhere; production keeps plugin 1.0.1 until R1. If overridden: add a short section that runs the wrappers after the same price-and-yes step.
2. **Version 2.0.0** in `plugin.json` and `marketplace.json` (matching the server's 2.0.0 at R1), plus a marketplace `metadata.description` (the validator's only warning). If overridden: change both manifests and the CHANGELOG heading.
3. **Price shown from `estimate_run`.** The skill always prices with `estimate_run` (intent `screen` for a new project; `create_project`'s quote has no per-scope options) and shows each option's scope, the expected cost "about $X" and `payer.label`. The user picks the scope; the skill does not choose one. A changed price, payer or scope needs a new yes. **Amended 2026-10-12** (monorepo decision-log rows 86, 91): the expected cost (`expectedUsd`, else `priceUsd`) is the only price told to the user; `ceilingUsd` stays a machine field, never quoted (it was shown as "the most it may cost" before).
4. **The chat yes and the browser approval are both needed** when the server asks for approval; the agent never opens or approves an `approvalUrl` itself.
5. **"Check incomplete, not charged"** as the user-facing words (Rule 1 of 0.4); for the user's own OpenRouter key the skill adds that the provider's tokens for the failed attempt cannot be refunded, because "not charged" would otherwise be untrue for that payer. A second rerun asks first. **Amended 2026-10-13** (monorepo memory `funds-graceful`, decision-log row 119): a check stopped because the payer's key ran dry is charged what it spent, does not rerun, and Check again on the same payer continues it at no cost for the answers it kept; a cancelled check is charged what it spent.
6. **"gate" stays a protocol word only.** The skill passes `gate` letters to tools and says "what L1 needs" / "what L2 needs" to people.
7. **Review-UX lane** (a separate Codex branch, not edited): kept supplementary files (`supplementaryKeys` / `supplementaryNames`, no claim of full coverage unless the tool says so) and the one total ceiling. Dropped `workflowView`, repository investigation (`deep_audit`, retired 2026-10-05) and its old level names.
8. **Commands keep their names** (`/repoready:analyze`, `/repoready:status`) so existing users' habits keep working; `analyze` now checks through the 2.x flow and accepts a paper link; `status` adds `list_updates` and the current repository's level line.
9. **Zip exclusions** use patterns that also catch nested folders (`'*node_modules/*'`, `'*venv/*'`, `'*__pycache__/*'`, `'*.ipynb_checkpoints/*'`, `'*.env'`, `'*.env.*'`), tested with Info-ZIP on macOS. `.env.example` files are excluded too (on the safe side).
10. **Helmholtz entry (C.3)**: the text that must change was recorded in the 2026-10-10 hand-off of `docs/DEVELOPMENT_CONTEXT.md` (now in Git history) for the monorepo plan's C.3 and is prepared on the Helmholtz fork's entry branch; the Helmholtz entry itself is changed only by a pull request to that marketplace.
11. **No "Confirm this" (2026-10-12, monorepo row 92).** The `confirm` intent is retired on the server (`intent_retired`); the skill offers only "I fixed this" on one finding and says each check confirms its uncertain findings itself. An Unresolved issue (`notDecided`) has no check of its own. If the owner restores the paid Confirm (`userConfirm.enabled`), add the intent back to step 3 of the skill.
12. **The web app's state words (2026-10-12, row 93)** for findings and results: Missing, Warning, Unresolved, Available, Not applicable; Impact labels exactly as the server's `IMPACT_LABELS`, in its order.
13. **Scope labels "L1 check" and "L2 check" (owner 2026-10-13, relayed by the monorepo lead).** The user hears "L1 check" (are the code, data and software behind each result shared?) and "L2 check" (the full review without running the code: workflow, integrity, automation, reuse); the `scope` ids `materials` / `workflow` stay; "Materials" is only the area name. Where a server text still says "Materials and workflow", the skill tells the agent to say "L2 check".
14. **Supplementary results only on request; the rerun is conditional (2026-10-26, monorepo rows 200 and 126, checked against the production server).** By default a check does not check supplementary results (they are listed as not checked; the supplementary files are still read as materials of the main-text results). The skill may name each option's `supportingExtraUsd` ("+ about $Y") in one line, and only on the user's request estimates again with `check_supporting_results: true`; that quote's "about $X" includes the extra and needs its own yes; `start_run` takes no flag (it runs what the quote priced). "Check incomplete, not charged" may rerun once by itself; when it could not read some of the authors' code, only once that code is new. If the server adds a start-time flag or changes the rerun rule, change step 3 and the words section of the skill, the analyze command and the README.
15. **The to-dos come from `list_todos` (2.0.1, 2026-10-26, monorepo decision-log row 257).** Users could not see the to-dos: the server sent the to-do steps, their alternatives and Other findings only through `get_findings`, which the skill forbids. The server adds the read-only `list_todos` (the web app's To-dos plan); the skill, `/repoready:status`, `/repoready:analyze` and the README read it: goals To reach L1 / To reach L2 / Optional · beside the level, each finding's numbered steps, a step with alternatives as one step ("Either … or …"), done steps ticked, who can do each ("AI can fix this", "AI can help · needs your answer", "Authors"), "only what to do" as `status: 'open'`. `get_findings` / `get_report` stay forbidden; without `list_todos` (an older server) the skill falls back to `list_issues`. Publish 2.0.1 only after production serves `list_todos`.
